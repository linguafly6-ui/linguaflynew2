## Detailed findings

### 003–010: first standalone family

The extracted panel archive preserves the static source markup and visible text for Grammar, Pronunciation, Reading, Listening and Speaking. The original inline scripts are retained separately so dynamic question generation and audio/recording behaviour can be traced.

- Reading passages exist in the source HTML.
- Listening is a quiz with ten legacy questions and delayed transcript reveal, not the canonical ten-gap inline word-bank interaction.
- Grammar and Pronunciation content is present in the static panels, but this extraction does not certify canonical counts or the quality of every item.
- Speaking is vocabulary selection and recording, not ten independent prompts with individual model answers.
- No Writing panel is present in this family.

### 011–020: early data-driven family

- Mission data objects include Vocabulary, Pronunciation activity metadata, Grammar (three explicit items), Reading passage text and Listening script text.
- Reading and Listening prompt arrays each contain ten generic templates repeated across missions. They are not ten distinct, authored comprehension questions tied to each passage/script.
- Explicit Writing arrays contain 21–23 targets per mission. These are legacy letter-by-letter dictation data, not the canonical ten-target exercise set.
- Source answer arrays and prompt templates remain audit-only.

### 021–040: data-driven family with Writing payloads

- Mission data objects and explicit Writing target arrays have been preserved.
- Writing arrays contain 21–23 legacy targets per mission.
- Grammar source banks generally contain four items, below the canonical ten.
- The full mission object preserves available Reading and Listening fields; absence of a field must not be filled by inference.
- The Writing target count and legacy interaction need editorial selection/re-authoring to reach the canonical ten whole-word/phrase dictations.

### 041–070: shared runtime family

- Mission objects preserve Vocabulary, Pronunciation metadata, Grammar and available Reading/Listening source data.
- Grammar generally has four authored source items.
- Reading and Listening data arrays generally contain ten MCQs each; Listening is still not the canonical gap-fill.
- Writing is generated by shared runtime code, not by a mission-specific ten-item dictation payload. The shared runtime sources have been preserved.
- Vocabulary/Pronunciation counts vary. Mission 054 contains 26 vocabulary entries and must be editorially curated rather than blindly truncated.

### 071–100: second standalone family

- Static source panels contain Pronunciation and Speaking only.
- The pages do not provide canonical Grammar, Reading or Listening panels.
- Writing is dynamically generated by inline JavaScript as open-ended composition stages. It is not ten audio dictations.
- Speaking is a vocabulary-selection/recording flow, not ten distinct prompt/model-answer cards.
- Inline scripts are archived for reproducibility and further review.

## Safety, verification and non-claims

- The extraction records were parsed from files on `main`; mission objects were JSON-parsed, and section/script content was retained without manual re-authoring.
- The five standalone Practice extraction batches were separately re-read and verified: 38 missions, 1,900 entries, ten vocabulary pairs per mission, 50 Practice entries per mission and three options per entry.
- The source archives include answer-bearing material. They are editorial audit records only and must never be served directly to students.
- TTS calls/directives do not prove that real audio assets exist or that the British voice is available on a given device.
- No browser, microphone, real audio, accessibility or visual regression tests were run.
- No canonical JSON missions were created from these newly extracted records. No mission is newly certified as converted.
- The next step is editorial gap analysis and authoring: create missing Grammar/Reading/Listening/Writing/Speaking content where the source does not satisfy the fixed canonical template, then validate each canonical mission before UI migration.
